ROU SPA｜四步預約、手機版與顧客預約管理更新

這是完整的專案源码和正式構建，不是只包含替換檔案的小補丁。
本次已完成來源修改與驗證，並於 2026-10-01 將 003 migration 套用至正式 Supabase。
網站沿用原本 GitHub → Vercel 的發布設定。以下保留其他環境的部署與回復說明。

更新已有網站（請按順序）
1. 保留現有 Vercel 專案設定與環境變數，提交此包的來源變更到原本專案。
2. 用專案擁有人帳號開啟 Supabase SQL Editor，在對應網站的同一個專案執行：
   supabase/migrations/202610010003_customer_booking.sql
   003 可以重複執行。不要重跑原始 001、002，不要執行 cutover/bootstrap-owner 作為這次更新的一部分。
3. 專案根目錄使用 Node.js 24（至少 22.12），執行：
   npm ci
   npm test
   npm run build
4. 使用原本 Vercel 設定部署：Vite、Build Command npm run build、Output Directory dist。
   VITE_SUPABASE_URL 與 VITE_SUPABASE_ANON_KEY 沿用現有正確值；環境變數變更後必須重新構建。
   不要在前端加入 privileged/service role key。本包 dist 是依目前來源的公開設定構建。
5. 部署後在手機檢查：預約入口 → 四步預約 → 成功私人連結；查詢手機＋完整姓名 → 改期／取消；
   後台在相同日期範圍核對同一筆 ROU 預約編號，點重新整理或等下一次 15 秒更新。
6. 分別核對未來、已結束、已完成、已取消和凌晨跨日的記錄。列表與排程都會依台灣時間變灰。
   單純時間到期不會自動寫成 completed，也不會改動結帳／會員 credits。

若資料庫是全新空白專案：依 README 的初次部署流程，先執行 001、002、003，再設定第一位店主。
不要把「全新初始化」流程用於已經營運的資料庫。

業務規則
- 查詢需要完整手機＋目前後台顧客檔案的完整姓名；這是使用者指定的匹配方式，不含簡訊驗證。
- 相同手機沿用既有顧客檔案。若最新預約填了不同姓名，以私人預約連結管理该次預約，或由門店核對姓名。
- 查詢權限在記憶體保留 20 分鐘，過期需重新查詢；查詢每手機每 10 分鐘最多 10 次。
- 取消／改期使用既有提前修改期限，預設 24 小時。改期保留訂單編號、療程、原定時長／緩衝與價格。
- Active：服務結束時間未到，且不是 completed、cancelled、no_show。
- Nonactive：服務已結束，或已完成、取消、未到店。按完整時間戳判斷，不只按當天日期。
- 同步是寫入同一套 spa_appointments，再由前／後台輪詢讀取；不是向舊表 bookings 雙向複製。
- 原本預設台灣今天至＋6 天，共七天，及每 15 秒後台更新已保留。

若仍看不到一筆預約
依 ROU 編號、服務營業日期和登入角色核對。技師帳號只看到自己的預約。
凌晨時段歸前一營業日；日期範圍外不會顯示。舊後台若仍讀 bookings，不會收到新表的持續更新。
可由資料庫擁有人執行 supabase/diagnose-booking-readonly.sql 核對，不要為了刷新重跑 migration。

回復
先將網站來源回復到更新前版本並重新部署。003 的新增表／RPC 可保留，它不刪除既有資料，也不改寫舊登入設定。
已成功取消／改期的資料屬正式業務變動，不應直接還原資料庫備份；如需修正，透過門店正常流程處理。
