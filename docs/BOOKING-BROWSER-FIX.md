# 訪客預約卡在「預約中」修復

日期：2026-10-10

## 查到的問題

1. 預約提交直接呼叫 `crypto.randomUUID()`，而且呼叫位置在錯誤處理範圍外。不提供此 API 的瀏覽器會拋出例外，沒有送出預約請求，按鈕卻永久保持「預約中」。
2. 公開接口沒有等待上限，連線無回應時可能一直等待。
3. 提交失敗的提示與時段載入共用狀態；背景重新載入時段會清除提示，讓顧客無法知道失敗原因。

匿名訪客的正式提交接口並未限制為店主使用：本次未登入後台的測試預約得到 HTTP 200，隨即取消得到 HTTP 204。測試預約已釋放時段。

## 修改

- `src/lib/request-id.js`：共用安全 UUID 產生器。優先使用原生 API，否則使用 `crypto.getRandomValues()` 產生 UUID v4；不使用 `Math.random()`。
- `src/PublicBookingExperience.jsx`：操作編號產生納入 `try/catch/finally`，任何失敗都恢復按鈕。提交提示獨立保存，背景時段更新不再將其清除。
- `src/lib/public-rpc.js`、`src/lib/spa.js`：公開接口最多等待 25 秒，取消逾時請求，提供連線／逾時提示，保持公開金鑰及匿名身分，不攜帶後台會話或 Cookie。
- `src/BookingLookup.jsx`、`src/App.jsx`：顧客改期／取消及原預約處理改用相容編號；編號例外納入錯誤處理。
- `src/OperationsShared.jsx`、`src/Attendance.jsx`、`src/BusinessOS.jsx`：使用同一個安全編號產生器，消除其他操作對原生 UUID API 的直接依賴。
- `ROU_SPA_OPERATING_MANUAL.md`：補充公開預約相容性、逾時與重試規則。

## 驗證

- 完整 `npm test` 與 production build 通過。
- 新增 17 項公開客戶端檢查：安全編號、匿名請求、回執、API 錯誤、斷線、等待回應與讀取回應本文逾時、相同操作編號重送等。
- 在瀏覽器停用原生 `randomUUID` 後，舊版可重現「預約中」、無錯誤提示、零提交請求。
- 修正版 production build 在同樣條件下能送出並顯示成功回執；故意斷線時保留姓名／手機、顯示提示並恢復按鈕，重送沿用同一操作編號。
- 瀏覽器介面相容性測試攔截建立預約請求，使用明確測試回執，不新增正式預約。

本次未取得對方 Firefox 的版本及原始錯誤記錄。上述測試確認並修復能造成相同症狀的問題，不能推定所有設備原本都只有同一原因。新版若發生網路問題會顯示具體提示，可依提示繼續判斷。

## 重試規則

逾時不表示伺服器一定沒有建立預約。保持相同資料再次提交會沿用原操作編號，由資料庫回傳原回執，避免重複建立；也可先使用「查詢預約」。只有顯示成功回執才視為提交完成。
