## 2. 系統設計與權限

採用「人員檔案 → 獨立登入帳號 → 日程中的服務歸屬 → 本人業績與評價」的關聯。人員資料與登入啟用狀態分開，停用帳號不會刪除歷史療程、評價或帳務。

| 功能／資料 | 店主 owner | 主管／櫃台／技師 |
| --- | --- | --- |
| 全店日程、日期篩選、搜尋、排程 | 查看與管理 | 只讀 |
| 新增／改期／取消／完成療程 | 可以 | 不可以 |
| 會員姓名、電話、等級、儲值餘額、到店次數 | 查看與管理 | 只讀 |
| 會員套票名稱、剩餘次數、有效期 | 查看與管理 | 只讀 |
| 會員內部備註、完整錢包流水與交易明細 | 可以 | 不提供 |
| 收款、退款、收支、支出、CSV 匯出 | 可以 | 不可以 |
| 人員職稱、薪酬、提成、帳號、排班 | 可以管理 | 不能管理 |
| 自己的職稱、薪酬設定、提成比例 | 可以 | 只讀本人 |
| 自己的完成療程、服務分鐘、提成估算、評價 | 可以 | 只讀本人 |
| 其他人薪酬、評價細節和私人連結 | 可以 | 不提供 |
| 門店設定、評價審核、權限稽核 | 可以 | 不可以 |

角色名稱仍保留「主管、櫃台、技師」，符合人員身分管理需求；依本次要求，三種角色使用相同的只讀工作台。職稱是另外的自由文字欄位，修改職稱不會增加權限。新增／修改帳號不能選 owner，現有 owner 也不能透過人員管理被降權或移除。

限制同時放在前端與資料庫：員工即使直接呼叫原本的新增、結帳、退款、報表或角色接口，資料庫也會拒絕。日程和會員回應採必要欄位白名單，不會把管理 token、評價 token、結帳金額或內部備註傳給員工。

## 3. 店主日常操作

### 設定人員與薪酬

1. 用原本店主信箱與密碼登入 `/#admin`。
2. 開啟「人員管理」，在既有人員卡片選擇編輯。
3. 設定職稱、月薪／時薪／每堂薪酬、薪酬金額及提成百分比。
4. 核對可服務療程、每週班表、休假和接單狀態，再儲存。

薪酬金額可留空表示尚未設定。這裡保存的是薪酬約定，不是已發薪紀錄；沒有自動計算出勤薪資或執行付款。

### 建立或管理登入

1. 在相應人員卡片選擇「建立登入帳號」。
2. 填入使用者名稱、密碼、角色與登入啟用狀態。
3. 員工在同一個 `/#admin` 入口使用這組使用者名稱／密碼登入。

使用者名稱為 3–32 個英文字母、數字、點、底線或連字號，第一個字元需為英文字母或數字，大小寫視為相同。密碼為 12–128 個字元。系統不顯示已保存密碼；忘記密碼由店主重設。

建立後可以調整角色／登入狀態、修改使用者名稱或重設密碼。密碼重設和停用會使舊後台存取令牌失效；停用狀態每次資料讀取都會重新檢查。

### 封存與恢復

「封存人員」用於離職或暫停合作，保留原姓名、ID、預約、評價與交易歸屬。尚有未結束有效預約時，系統要求先安排相關預約，避免已預約顧客失去技師。

封存同時關閉接單與後台登入。可在封存清單恢復；恢復後仍維持停止接單／禁止登入，由店主另行確認再啟用。這比永久刪除更適合需要保留營運歷史的門店。

## 4. 員工登入後看到什麼

- **日程**：全店預約時間、顧客姓名／電話、療程、技師、床位、狀態。保留日期快捷切換、搜尋、篩選和每 15 秒更新，沒有編輯與收款控制。
- **會員資訊**：會員基本資料、credits 金額餘額、到店次數、最後到店時間，以及套票剩餘次數與有效期。金額儲值和療程次數分開顯示，不能更改餘額。
- **我的資料**：本人職稱、已設定薪酬、提成比例、累計完成堂數；日期區間內的完成堂數、服務分鐘、已結帳提成估算、評分及評價；自己的班表與休假。預設區間為本月初到台灣今天。

提成使用結帳時保存的提成快照，退款療程不計入目前提成估算。修改人員提成比例不會重算過去已結帳療程。服務完成堂數與提成不混算：已完成但尚未結帳的療程可計堂數，沒有已結帳提成。評價區最多列出最近 100 筆本人評價，不顯示顧客私人聯絡資訊。

## 5. 顧客評價流程

1. 店主核對療程確實完成，將狀態設為「已完成」。
2. 顧客以原本手機＋完整姓名查詢預約，或開啟預約私人連結。
3. 在 Nonactive 的相應預約按「評價服務技師」。
4. 選擇 1–5 星，填寫最多 1,000 字體驗，提交後顯示「已評價」。
5. 評價綁定該次療程實際技師；員工本人可查看，店主沿用既有審核／公開／隱藏／回覆流程。

每筆完成療程只接受一次評價。後端核對查詢權限所屬顧客／預約，不能替其他人的療程評價。查詢結果不暴露永久評價 token。既有私人評價連結和會員頁仍可使用，提交後的狀態會同步顯示。

Nonactive 包含多種狀態，並不代表都已服務：取消、未到店和僅結束時間已過的預約均不能評價；時間到期不會自動改成完成或修改帳務。

## 7. 帳號與部署機制

員工不需要綁定個人信箱。Supabase Auth 內部使用不可收信的專案專用別名，员工只接觸使用者名稱。別名由伺服器依人員 ID 建立，前台不提供或要求輸入；沒有寄送邀請信或預設公用密碼。

登入接口先在伺服器解析啟用的人員使用者名稱，再交由 Supabase Auth 驗證密碼，回傳正常 session。未知名稱、停用帳號和錯誤密碼對外使用相同登入錯誤；每個名稱每 10 分鐘最多 20 次嘗試，並保留 Supabase Auth 本身的限制。沒有新增 IP 級分散攻擊防護，後續可加入邊緣流量限制或驗證碼。

只有 `staff-accounts` 伺服器函式可使用 Auth Admin 能力。每次請求先透過 Auth 驗證登入使用者，再確認資料庫中的 owner；帳號資料與密碼不能由前端直接修改 Auth 管理接口。密碼不寫入業務表、稽核內容或回應。

兩支函式使用 Supabase 內建的伺服器環境變數，沒有把 service role key 放入官網或 Vercel 的 `VITE_*`。函式的 legacy JWT gateway 設為關閉，以支援目前 Auth 簽章；管理函式仍明確驗證登入 token 和店主權限，登入函式則驗證密碼。此方式依 Supabase 的 [Edge Function 部署說明](https://supabase.com/docs/guides/functions/quickstart-dashboard)、[伺服器環境變數](https://supabase.com/docs/guides/functions/secrets)、[建立使用者](https://supabase.com/docs/reference/javascript/auth-admin-createuser)和[更新使用者](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid)接口實作。

手動 SQL 部署不會自動填入 Supabase CLI 的 migration 歷史。日後切換 CLI 時，先將已部署的 001–004 標記為 applied，避免重新初始化既有資料。004 已在隔離資料庫驗證可重複執行。

### 其他環境更新順序

1. 已有 001–003 的資料庫只執行 004；不要重跑初始化、舊資料匯入或 bootstrap-owner。
2. 部署 `staff-accounts`、`staff-login`，沿用內建伺服器變數及設定檔的函式驗證配置。
3. 執行 `npm ci`、`npm test`、`npm run build`，由現有 GitHub／Vercel 流程發布來源。
4. 店主登入核對原本人員與會員；再為需要登入的員工建立帳號。

只回復舊前端會令舊主管／櫃台的寫入頁面被新資料庫拒絕，應以修補發布處理相容性；不要為了回復畫面撤回資料庫的權限限制。封存及登入停用可由店主恢復，不需刪除歷史資料。

## 9. 下一階段可完善的業務功能

本次把人員帳號、只讀工作台和評價流程落地。若要繼續走向完整門店管理系統，建議依營運需要分階段加入：

1. **服務交班與提醒**：到店提醒、技師今日工作清單、交班備註與待辦；若要讓櫃台或主管寫入，另設明確可授予的權限，先由店主決定。
2. **薪資與提成結算**：月份鎖定、出勤核對、分段／指定療程提成、退款調整、店主確認結算與已發薪記錄。現在的配置和估算不能替代正式薪資發放。
3. **會員維護**：回訪計畫、服務偏好、套票到期提醒和會員本人註冊；敏感服務備註應再依角色細分。
4. **評價營運**：低分待辦、店主回覆時效、期間評分趨勢；保持逐次療程驗證與公開內容審核。
5. **安全與維運**：登入 IP 限流、必要時多因素驗證、備份恢復演練、部署告警與審計查詢。

商品部分維持目前狀態，沒有擴充商品或購物功能。
