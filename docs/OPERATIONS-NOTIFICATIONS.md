# Operations reminders

`OperationsNotifications` stays mounted for an authenticated, authorized Admin account across page changes. Its `userKey` is the signed-in user ID; `enabled`, `allowed(module)`, `onNavigate(module, context)` and `onAccessDenied()` come from Admin. Account changes remount the reminder baseline and discard local dismissals and timers.

The bottom-right circular coffee-and-gold bell is always visible, including when there are no tasks or a read fails. Its badge shows the number of nonzero reminder categories, rather than a sum that could count one booking more than once. Desktop mouse hover opens the complete list; the pointer can travel across the gap into the panel without closing it. Leaving closes a hover-only panel after 200ms. Clicking pins the panel open, and clicking again closes it; touch devices use the same tap toggle. Opening it lists every currently permitted category with title, urgency, count and a link into the existing protected workflow. Popups contain no booking, customer, staff or financial details.

The first successful snapshot is silent. Later category changes use an opaque server `revision`, count and urgency; changing only a server timestamp or navigation cutoff does not repeat a reminder. Same-count replacement of an underlying task changes its revision. Resolved reminders immediately disappear. Dismissal lasts in memory until that category changes or reappears. At most three popups display, each for eight seconds; mouse hover or keyboard focus pauses dismissal. The complete list remains available from the bell.

Opening reminders never takes keyboard focus. Enter/Space on the bell opens it, and Escape anywhere inside the reminder surface closes it and returns focus to the bell. The close button does not immediately reopen on hover. Clicking or moving keyboard focus outside closes the panel without taking focus back. All actions are regular buttons. Toast announcements use polite status messages. The panel is a nonmodal region; native editing dialogs remain in the browser's top layer above reminders. The surface fits 320px screens and independently scrolls long lists.

`useOperationsSnapshot({ enabled = true, userKey, refreshToken })` returns `{ data, busy, error, forbidden, refresh, status, pending }`. The board and bell share an account-keyed read queue for `spa_operations_convenience`. Initial reads and repeated identical `refreshToken` values are deduplicated, and hints received during a request schedule one catch-up read. The store owns one shared Realtime subscription for all operations scopes, regardless of consumer count. Its refresh controller checks visibility and connectivity and can update while editing: this read-only snapshot does not replace any form state.

There is no periodic polling. Successful snapshots may supply `next_refresh_at` and `server_time`; one timeout reads again at that actual schedule or date boundary. Realtime changes and reconnect/visibility catch-up also read the snapshot. Temporary errors preserve the last successful data with an explicit status; `FORBIDDEN` clears it and sets `forbidden: true`. That signal stays set until a successful authorized read. The notification component calls `onAccessDenied()` once per transition into the denied state in a layout effect, before the next paint. Admin uses that callback to clear open forms, page data and catalog and revalidate access even if its ordinary refresh is paused for editing. Removing the last subscriber clears the cache and boundary timer and ignores outstanding responses.

Verification: `node scripts/test-operations-notifications.mjs` covers initial silence, count and identity changes, timestamp stability, permission filtering, resolution, queue limits, shared initial requests, catch-up reads, exact boundary timing, failures and logout races.
