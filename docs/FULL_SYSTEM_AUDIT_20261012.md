# ROU SPA 前後台完整檢查與優化報告

核對日：2026-10-12。公開預約版本：`20261012-01`。

本次檢查包含顧客、員工、店主三種身份，以及官網、管理後台、資料庫接口與 iOS 共用程式。重點是操作能否完成、失敗時是否能恢復、跨模組資料是否同源、權限是否在伺服器驗證。保留目前咖啡色／金色視覺和既有業務制度。

## 1. 結論

現有預約、排班、出勤、會員、POS、薪資等主要流程已有共同資料來源與交易保護。本次找到的實際問題集中在「網路失敗後沒有恢復入口」、「資料重設和備份不同步」、「少數舊財務操作的重試驗證不足」及「公開身分核對可繞過嘗試限制」。這些問題已修正，並增加可重現的自動驗證。

這不是所有真實裝置、所有併發情況都已證明無誤的保證。正式環境以只讀驗收為主，不用真實會員與收款資料執行破壞性測試；退款、重設、權限拒絕與失敗回滾使用隔離的 PostgreSQL 測試資料。

### 不應混為一談的規則

- 接客 4 人是可設定的**建議同時容量**；仍有合格空閒技師時允許超量申請，強制待確認並提醒電話協調。它不能繞過技師時間／技能衝突，不代表無限超賣同一位技師。
- 班表代表計畫，不代表已打卡或已完成療程；時間到了不自動標記完成或自動核准工時。
- POS 現在是立即結款記錄；「本次應收」不是可掛帳的完整應收帳款系統，刷卡／轉帳選項也不會實際向銀行扣款。
- 薪資、營業收入、現金收支使用不同的日期與認列口徑；儲值／套票購買的現收不等於當日服務收入。應先看操作手冊的口徑表，不能只因數值不同就判定不同步。
- 員工的職務／職稱／聘僱分類與網站宣傳顯示不同；薪資按有效制度及成交／結算快照計算，不能以宣傳職稱文字判薪。

## 6. 值得下一輪做的優化

以下是尚未實作的產品或系統改進，不能視為本次功能已上線。

### 優先：恢復能力與日常收款

1. **備份恢復演練。** 現有 JSON 是資料導出，沒有一鍵恢復。先建立隔離資料庫恢復流程、關聯完整性驗證與操作記錄；日常資料庫備份也應核對能否實際恢復。
2. **POS 一般退款／退貨。** 補上訂單及逐項退款入口、是否回補可售庫存、人員提成沖回、優惠券／儲值恢復與薪資鎖定檢查。現有「刪除／重設」不能替代客人退貨。
3. **日結交班。** 依現金、刷卡、轉帳展示系統金額、實際盤點及差異原因，保存交班快照，避免將收支淨額當獲利。
4. **集中操作編號登記。** 新加值等接口已有完整內容去重，但各歷史模組不完全採同一命名空間；例如既有退款對他類 UUID 的處理仍不同。現行隨機編號碰撞機率很低，下一輪可用集中表保證全模組一致，並加真正多連線競爭測試。

### 其次：更清楚的操作畫面

5. **統一頁面工具列與手機列表卡片。** 各模組統一「期間、搜尋、狀態、新增、匯出」位置；資料多時手機展示重點卡片，可展開詳細欄位，減少寬表的橫向閱讀。
6. **門店總覽聚焦下一個動作。** 把已排班未打卡、超容量待聯絡、療程完成待結帳、待核准班表／補卡保持為可直接處理的入口；跨午夜和逾時判斷清楚標示業務日期。
7. **會員價明確啟用或隱藏。** 目前保存的會員價不能一概認為已套用在所有交易；若要真正啟用，應定義與折扣、優惠券、套票的優先順序，並保存成交快照。
8. **應收帳款依業務需求獨立建立。** 若要掛帳，需有欠款、部分收款、到期、收款沖抵及核銷；不能只把 POS 的「本次應收」改名字就完成。

### 系統與安全維護

9. **可追查的故障記錄。** 客戶端／服務端記錄匿名錯誤碼、發布版本、操作編號及耗時，不記錄姓名電話、密碼或位置；讓門店可以提供查詢碼定位問題。
10. **顧客身份強化。** 現行姓名＋手機仍不是手機所有權驗證。若要提高會員財務資料保護，可設計 LINE 驗證或手機一次性驗證碼，保留門店人工協助；需要先確認登入體驗、費用和恢復流程。
11. **店主管理安全。** 核對店主強驗證、外洩密鑰替換及權限定期複核；本次沒有擅自更換任何密碼或憑證。新建 private 函式仍須明確撤銷瀏覽器執行權並跑安全測試。
12. **程式拆分與資料量測試。** 清理首頁已停用的舊預約 markup，拆分大型管理頁；大量會員／流水用分頁或按需讀取，避免整份 JSON 長期增大。Excel 匯出維持按需載入。
