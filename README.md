# 柔療髮浴 · 門店營運系統

沿用原本 React／Vercel 官網設計，將預約與門店營運接上 Supabase PostgreSQL。商品區沿用現況，這次不擴充商品功能。

## 這一版能做什麼

| 模組 | 已實作 |
| --- | --- |
| 預約 | 真實可用時段、4 個床位、技師技能／排班／休假、療程時長＋清潔緩衝、自動分配或指定技師、手動／自動確認、改期、到店、完成、取消、未到店 |
| 會員 | 顧客檔案、服務偏好備註、到店歷史、儲值金額 credits、療程次數套票、有效期、充值／扣款／退款流水、登入後查看自己資料 |
| 員工 | 介紹／技能／接單狀態、每週排班與休假、完成次數、服務分鐘、療程收入、提成估算、評分及評價數 |
| 評價 | 完成療程後的私人評價連結、每次療程一次評價、審核／公開／隱藏、店家回覆、官網顯示已公開評價、匿名反饋處理 |
| 收支 | 現金／刷卡／轉帳記錄、儲值與套票預收、療程收入、折扣、獨立小費、全額退款恢復 credits、費用支出、每日收支、CSV 匯出 |
| 權限 | Supabase 真實登入、店主／主管／櫃台／技師、會員只能看自己的帳戶、操作稽核、後端驗證與交易保護 |

入口：`/#admin`、`/#member`。顧客預約和評價使用不可猜測的私人連結，請勿公開分享。

## 設計參考與下一步

參考 [Fresha 的預約、團隊、客戶及報表模組](https://www.fresha.com/for-business/features) 和 [Zenoti 的 spa 管理功能](https://www.zenoti.com/spa-management-software)，採用「一次療程串起顧客、技師、床位、收款與評價」的記錄方式。

這一版先打通單店營運核心。下一階段建議依順序加入：

1. LINE／Email／簡訊確認與到店提醒、候補名單。需另接通知供應商，取得通知同意，避免重複發送。
2. 線上訂金／支付與退款接口。驗證供應商回傳簽章，不能以瀏覽器付款成功畫面作為收款依據。
3. 預約防濫用驗證與限流。現有資料庫含基本提交限制，尚未提供 IP 限流、手機驗證或 CAPTCHA。
4. 日結交班、零用金／現金盤點、憑證附件、儲值／套票購買退款及部分退款。現版本只提供療程結帳的全額退款，不能直接刪除帳務流水。
5. 經店主確認的提成／小費分配規則、實際薪資發放與成本。收支淨額不等於會計利潤；提成目前為估算。
6. 會員分級權益、回訪／流失分析、生日活動；多分店等業務擴充。

## 初次部署

1. 在 Supabase SQL Editor 依序執行 `supabase/migrations/202610010001_spa_operations.sql`、`202610010002_legacy_import.sql`。**只能執行一次，不要重跑。** 舊表不刪除。
2. 在 Authentication 建立店主帳號，密碼由帳號持有人設定。將 `supabase/bootstrap-owner.sql` 的 `OWNER_EMAIL_HERE` 換成該帳號 email 後執行，授予第一位店主。不要將真實密碼、service role key 或個人 email 提交到公開 GitHub。
3. Vercel 使用 Vite，Build Command `npm run build`，Output Directory `dist`，Node.js 24（至少 22.12）。設定 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_ANON_KEY`；只放 publishable／anon 公開 key。網站含本專案的公開預設值，環境變數可覆蓋。
4. 部署後用店主帳號登入 `/#admin`，核對療程价格、員工真實資料、技能、排班、休假、4 床設定、取消與確認規則。保留官網原有六位技師和營業時間作為初始值，請按真實營運更新。
5. 門店設定中的「舊預約遷移」會列出每筆結果；無法對應的來源保存在 `spa_legacy_imports.original`。由店主在 Supabase Table Editor 核對原始資料，再透過正常營運流程補建正確记录；不要把未知的舊款項算成實收。
6. 確認新網站已部署且店主可登入後執行 `supabase/cutover.sql`，關閉舊匿名後台接口。原始預約仍留在資料庫，postgres／service role 可以存取。不要回滾到含舊共享密碼的版本。

若透過 SQL Editor 手動部署後改用 Supabase CLI migration，先將已執行的版本用 `supabase migration repair --status applied <version>` 標記，避免 CLI 再次執行。

## 日常操作

- **預約**：櫃台確認待確認預約 → 到店 → 技師完成 → 櫃台核對入帳後結帳。待確認也會占用床位，取消／未到店才釋放。線上預約最少提前 30 分鐘。
- **時間**：所有門店日期統一 `Asia/Taipei`；凌晨是前一營業日的「翌日」時段。療程與清潔緩衝必須在技師班表和門店結束前全部完成。
- **credits**：金額儲值與療程次數分開，不能混算；充值／售套票增加現金與預收，兌換時認列療程收入。套票限指定療程且不得與折扣同時使用，茶飲另計。退款恢復儲值／次數，沖回收入，實際退現金另外記錄。
- **會員登入**：先在 Authentication 建立帳號，主管將 User UUID 綁定會員檔案。手機相同會連結預約，但不會自動開放私人會員資訊。新會員頁沒有自行註冊功能。
- **員工登入**：先建立 Authentication 帳號，店主配置角色；技師角色必須對應員工。技師只看自己的預約／班表，櫃台可處理會員和收款，主管可看店務報表，店主可管理角色。
- **評價**：完成後複製顧客評價連結給顧客；提交後由門店審核。公開內容不含顧客姓名／電話。
- **帳務**：支付方式是人工確認的入帳記錄，沒有連接銀行、刷卡機或支付閘道。備註填收款憑證，月底以真實銀行／現金對帳。未使用儲值和套票額為目前值，不是報表期間末的歷史快照；套票到期不自動消除預收金額。

## 開發與驗證

```sh
npm ci
npm test
npm run build
npm run dev
```

資料庫測試在 PGlite 的 PostgreSQL 引擎執行，不連線或改動正式資料。涵蓋權限拒絕、4 床容量、完整重疊與緩衝、失敗交易回滾、重複提交、會員餘額、套票餘額與分攤尾差、結帳／退款、已完成評價、跨午夜和舊資料保存。GitHub Actions 執行同一套檢查。

## 後端維護

所有新表以 `spa_` 開頭並啟用 RLS，不給瀏覽器直接表權限。公開 RPC 僅開放目錄、可用時段、預約、持有私人 token 的單次預約／評價、匿名反饋和已公開評價；營運 RPC 在資料庫檢查 `spa_roles`。`spa_private` helper 不對 anon 開放。

交易鎖和資料庫 trigger 共同保護同一技師／床位的完整占用區間。價格、時長、茶飲費用、餘額及權限都由後端決定；瀏覽器不能直接指定實收或修改會員餘額。結帳保留價格與提成快照，帳務採追加流水，退款採沖銷。

正式營運需配置符合門店需求的資料庫備份／還原與監控；這次沒有購買付費方案或自動配置備份供應商。公開 key 不提供管理權限，privileged key 不得出現在任何前端檔案或 Vercel 的 `VITE_` 變數。
